# Effect of Code Representation Layers on LLM-Based Security Weakness Detection

**논문 정보**

- **논문명:** Effect of Code Representation Layers on LLM-Based Security Weakness Detection
- **저자:** Seojin Jeong, Hyunji Cho, Jinsoo Jang
- **소속:** Chungnam National University
- **연구 분야:** LLM, Software Vulnerability Detection, CWE, LLVM IR, Assembly Language

---

## 1. 연구 배경

최근 대규모 언어 모델(LLM, Large Language Model)의 코드 이해 및 추론 능력을 활용하여 소프트웨어 보안약점을 탐지하는 연구가 활발하게 이루어지고 있다.

LLM은 코드의 구조와 문맥을 분석하여 보안약점의 존재 여부뿐 아니라 발생 원인과 관련 CWE 유형까지 추론할 수 있다.

그러나 LLM 기반 보안약점 탐지에서 **입력 코드의 표현계층(Code Representation Layer)이 탐지 성능에 어떠한 영향을 미치는지**에 대한 분석은 여전히 부족하다.

동일한 프로그램이라도 C 소스코드, LLVM IR, Assembly와 같이 표현되는 계층에 따라 모델이 확인할 수 있는 정보가 달라진다.

| 표현계층 | 특징 |
|---|---|
| C Source Code | 변수명, 자료형, 조건문 등 고수준 의미 정보 포함 |
| LLVM IR | 컴파일러 중간 표현으로 연산과 제어 흐름을 명시적으로 표현 |
| x86-64 Assembly | 레지스터, 메모리 접근 및 분기 명령어 등 저수준 실행 구조 표현 |

기존 연구에서는 이러한 표현계층에 따른 LLM의 탐지 성능 차이를 비교했다.

이번 연구에서는 이를 확장하여 **표현계층뿐 아니라 LLM 모델에 따라서도 탐지 성능이 어떻게 달라지는지 분석하고, 오분류가 발생하는 원인까지 살펴보고자 했다.**

특히 모델이 보안약점을 탐지하더라도 정확한 CWE를 예측하지 못하는 경우가 존재한다는 점에 주목했다.

## 2. 연구 목적

본 연구의 목적은 세 가지 코드 표현계층에서 여러 LLM의 보안약점 탐지 성능을 비교하고, 오분류 사례를 통해 성능 차이의 원인을 분석하는 것이다.

이를 위해 다음 세 가지 연구 방향을 설정했다.

1. **코드 표현계층별 성능 비교:** 동일한 프로그램을 C, LLVM IR, x86-64 Assembly로 변환하고 탐지 성능을 비교한다.
2. **LLM 모델별 성능 비교:** 여러 LLM에서 코드 표현계층에 따른 탐지 성능 변화가 동일하게 나타나는지 확인한다.
3. **CWE 오분류 분석:** 잘못 예측된 CWE를 분석하여 표현계층 변화와 CWE 의미적 관계가 탐지 결과에 미치는 영향을 살펴본다.

또한 기존 공개 벤치마크에 포함된 코드가 LLM의 학습 데이터에 사용되었을 가능성을 줄이기 위해 자체 데이터셋을 구성했다.

## 3. 데이터셋 구성

### 3.1. 자체 제작 데이터셋

기존에 공개된 보안약점 데이터셋은 LLM의 사전학습 과정에서 사용되었을 가능성이 있다.

이 경우 모델이 실제로 코드의 보안약점을 분석한 것인지, 학습 과정에서 접했던 패턴을 활용한 것인지 구분하기 어려울 수 있다.

이러한 가능성을 줄이기 위해 본 연구에서는 10개 CWE 유형을 대상으로 자체 데이터셋을 제작했다.

각 CWE 유형마다 보안약점이 존재하는 프로그램 5개와 해당 보안약점을 수정한 프로그램 5개를 구성했다.

| 구분 | 개수 |
|---|---:|
| CWE 유형 | 10개 |
| 유형별 취약 프로그램 | 5개 |
| 유형별 수정 프로그램 | 5개 |
| 전체 테스트 케이스 | **100개** |

### 3.2. CWE 유형

실험에서 사용한 CWE는 다음과 같다.

| CWE | 보안약점 유형 |
|---|---|
| CWE-121 | 스택 기반 버퍼 오버플로 |
| CWE-190 | 정수 오버플로 또는 래핑 |
| CWE-367 | TOCTOU 경쟁 조건 |
| CWE-369 | 0으로 나누기 |
| CWE-400 | 제어되지 않는 자원 소비 |
| CWE-401 | 메모리 누수 |
| CWE-416 | 해제 후 사용(Use After Free) |
| CWE-476 | NULL 포인터 역참조 |
| CWE-481 | 비교 대신 대입 연산 사용 |
| CWE-835 | 무한 루프 |

각 프로그램의 정답 CWE는 데이터셋 제작 과정에서 의도적으로 구현한 보안약점 유형을 기준으로 지정했다.

또한 정적 분석 도구인 **Cppcheck**를 사용하여 의도하지 않은 추가 결함이나 다른 보안약점이 포함되지 않았는지 확인했다.

다만 Cppcheck는 정적 분석 도구이므로 모든 취약점의 실제 발생 여부를 검증하는 데에는 한계가 있다.

## 4. 실험 설계 및 방법

### 4.1. 코드 표현계층 구성

제작한 100개의 테스트 케이스를 세 가지 표현계층으로 구성했다.

- **C Source Code:** 원본 C 소스코드
- **LLVM IR:** LLVM 컴파일러 인프라를 이용한 중간 표현
- **x86-64 Assembly:** x86-64 명령어 기반 어셈블리어

각 표현계층에서 동일한 보안약점 사례를 사용하여 코드 표현 방식에 따른 성능 차이를 비교했다.

### 4.2. LLM 모델 선정

이번 연구에서는 다음 세 가지 모델을 사용했다.

- Claude Opus 4.8
- GPT-5.5
- Gemini 3.1 Pro

모델마다 코드 이해 및 보안약점 추론 능력이 다를 수 있으므로, 단일 LLM에서 관찰한 결과가 다른 모델에서도 나타나는지 확인하고자 했다.

세 모델에는 동일한 코드 표현계층과 평가 기준을 적용했다.

**[그림 1. 데이터셋 생성 및 코드 표현계층별 LLM 보안약점 탐지 실험 구성도 삽입]**

### 4.3. CWE 평가 기준

일반적으로 CWE 분류 성능은 모델이 예측한 CWE와 정답 CWE가 정확히 일치하는지를 기준으로 평가할 수 있다.

그러나 CWE는 서로 독립적인 분류만으로 구성되어 있지 않다.

일부 CWE는 상위·하위 관계를 가지거나 보안약점의 발생 원인과 결과를 설명하는 관계에 있다.

따라서 관련성이 높은 CWE를 예측했음에도 단순히 번호가 다르다는 이유로 모두 오분류 처리하는 것은 모델의 분석 결과를 충분히 반영하지 못할 가능성이 있다.

이러한 점을 고려하여 본 연구에서는 MITRE CWE의 계층 구조와 설명을 바탕으로 제한적인 CWE 관계를 사전에 정의했다.

| CWE 관계 | 유형 |
|---|---|
| CWE-120 ↔ CWE-121 | 계층적 관계 |
| CWE-400 ↔ CWE-401 | 계층적 관계 |
| CWE-131 ↔ CWE-122 | 원인·결과 관계 |
| CWE-190 ↔ CWE-197 | 원인·결과 관계 |

모델이 정답 CWE와 정확히 일치하는 유형을 예측하거나, 사전에 정의한 관련 CWE를 예측한 경우 정답으로 인정했다.

다만 유사한 CWE를 폭넓게 인정할 경우 평가 결과가 인위적으로 높아질 수 있으므로, 정의된 네 가지 관계 이외에는 정확한 CWE 일치를 요구했다.

즉, **CWE 간 의미적 관계를 평가에 반영하되, 정답 인정 범위를 제한하여 평가의 일관성을 유지하고자 했다.**

### 4.4. 입력 순서에 따른 영향 확인

테스트 케이스의 입력 순서가 실험 결과에 영향을 미칠 가능성을 확인하기 위해 입력 순서를 역순으로 변경하여 실험을 반복했다.

기존 순서와 역순으로 진행한 실험에서는 전반적으로 유사한 성능 경향이 나타났다.

이를 통해 이번 연구에서 관찰한 표현계층별 성능 차이가 테스트 케이스의 입력 순서에 의해 크게 달라지지 않았음을 확인했다.

### 4.5. 평가 지표

모델별 탐지 성능은 Accuracy, Precision, Recall, F1-score를 사용하여 비교했다.

또한 Gemini 3.1 Pro에서는 안전 정책에 의해 응답이 거부되는 사례가 발생했다.

이러한 응답은 **ABSTAIN**으로 분류하고 성능지표 계산에서 제외했으며, 그 개수는 별도로 기록했다.

## 5. 실험 결과 및 분석

### 5.1. 모델별 탐지 성능

세 모델에 대해 코드 표현계층별 보안약점 탐지 성능을 측정한 결과는 다음과 같다.

**[표 1. 코드 표현계층 및 LLM별 보안약점 탐지 성능]**

| Model | Layer | Precision | Recall | F1 | Accuracy |
|---|---|---:|---:|---:|---:|
| Claude Opus 4.8 | SRC | 0.784 | 0.800 | 0.792 | 0.790 |
| | IR | 0.744 | 0.640 | 0.688 | 0.710 |
| | ASM | 0.702 | 0.660 | 0.680 | 0.690 |
| GPT-5.5 | SRC | 0.816 | 0.800 | 0.808 | 0.810 |
| | IR | 0.660 | 0.700 | 0.680 | 0.670 |
| | ASM | 0.694 | 0.680 | 0.687 | 0.690 |
| Gemini 3.1 Pro | SRC | 0.791 | 0.756 | 0.773 | 0.780 |
| | IR | 0.829 | 0.708 | 0.764 | 0.777 |
| | ASM | 0.825 | 0.688 | 0.750 | 0.761 |

*SRC: Source Code, IR: LLVM IR, ASM: Assembly. Gemini 3.1 Pro의 ABSTAIN 응답은 지표 계산에서 제외했다.*

### 5.2. Claude Opus 4.8

Claude Opus 4.8은 C 소스코드에서 가장 높은 성능을 보였다.

- Source Code: Accuracy 0.790, F1-score 0.792
- LLVM IR: Accuracy 0.710, F1-score 0.688
- Assembly: Accuracy 0.690, F1-score 0.680

코드 표현계층이 저수준으로 변화할수록 전반적인 탐지 성능이 감소하는 경향이 나타났다.

이는 원본 소스코드에 포함된 고수준 의미 정보가 모델의 CWE 판단에 중요한 역할을 했을 가능성을 보여준다.

### 5.3. GPT-5.5

GPT-5.5 역시 C 소스코드에서 가장 높은 성능을 기록했다.

- Source Code: Accuracy 0.810, F1-score 0.808
- LLVM IR: Accuracy 0.670, F1-score 0.680
- Assembly: Accuracy 0.690, F1-score 0.687

특히 C 소스코드에서는 세 모델 중 가장 높은 Accuracy와 F1-score를 보였다.

반면 LLVM IR과 Assembly에서는 성능이 크게 감소했으며, Assembly가 LLVM IR보다 소폭 높은 성능을 기록했다.

이러한 결과는 **동일한 모델이라도 입력 코드의 표현계층에 따라 보안약점 탐지 성능에 상당한 차이가 발생할 수 있음**을 보여준다.

### 5.4. Gemini 3.1 Pro

Gemini 3.1 Pro는 다른 두 모델과 다르게 표현계층에 따른 성능 차이가 상대적으로 작게 나타났다.

- Source Code: Accuracy 0.780, F1-score 0.773
- LLVM IR: Accuracy 0.777, F1-score 0.764
- Assembly: Accuracy 0.761, F1-score 0.750

특히 Accuracy는 세 표현계층에서 0.780, 0.777, 0.761로 나타나 상대적으로 일정한 성능을 유지했다.

또한 Precision은 LLVM IR에서 0.829로 가장 높았으며, Assembly에서도 0.825를 기록했다.

이는 Gemini 3.1 Pro가 다른 두 모델과 달리 저수준 코드 표현에서도 비교적 안정적인 탐지 성능을 보였음을 의미한다.

다만 Gemini 3.1 Pro는 안전 정책으로 인해 Source Code 9개, LLVM IR 6개, Assembly 8개의 응답을 거부했다.

이러한 사례는 지표 계산에서 제외되었으므로, 다른 두 모델과 결과를 비교할 때 주의가 필요하다.

### 5.5. 결과 종합

실험 결과, 코드 표현계층이 탐지 성능에 미치는 영향은 LLM 모델에 따라 다르게 나타났다.

Claude Opus 4.8과 GPT-5.5는 고급언어에서 가장 높은 성능을 보였으며, 저수준 표현계층으로 변환될수록 탐지 성능이 감소하는 경향을 나타냈다.

반면 Gemini 3.1 Pro는 세 표현계층에서 비교적 유사한 성능을 보였다.

따라서 **코드 표현계층에 따른 탐지 성능 차이는 모든 LLM에서 동일하게 발생하는 것이 아니며, 모델별 코드 이해 특성에 따라 달라질 수 있음**을 확인했다.

## 6. CWE 오분류 사례 분석

이번 연구에서는 단순히 Accuracy나 F1-score를 비교하는 것에서 나아가, 모델이 어떤 CWE를 잘못 예측했는지 분석했다.

그 결과 세 가지 주요 오분류 패턴을 확인했다.

### 6.1. CWE 개념 구분의 어려움

일부 보안약점은 코드 표현계층이 달라져도 동일한 CWE로 잘못 분류되었다.

대표적으로 **CWE-190(Integer Overflow)** 사례가 **CWE-191(Integer Underflow)**로 예측되는 경우가 있었다.

두 CWE 모두 정수 연산과 관련된 보안약점이지만 구체적인 발생 조건은 다르다.

이러한 결과는 모델이 정수 관련 보안약점이라는 공통적인 특성은 인식하더라도, 개별 CWE의 정의를 정확히 구분하지 못할 수 있음을 보여준다.

즉, 일부 오분류는 코드 표현계층 변화보다는 **CWE 개념 자체에 대한 모델의 이해 문제**에서 발생할 가능성이 있다.

### 6.2. 코드 표현계층 변환에 따른 정보 손실

코드 표현계층을 변환하면서 발생한 오분류도 확인되었다.

대표적인 사례는 **CWE-481(Assigning Instead of Comparing)**이다.

CWE-481은 비교 연산자를 사용해야 하는 위치에 대입 연산자를 사용하여 발생하는 보안약점이다.

원본 C 소스코드에서는 이러한 문법적 차이를 비교적 명확하게 확인할 수 있다.

그러나 LLVM IR이나 Assembly로 변환하면 원래 코드의 대입 및 비교 구문이 다른 형태의 연산으로 표현된다.

실험에서는 소스코드에서 대부분 올바르게 탐지되었던 CWE-481이 LLVM IR과 Assembly에서 다음과 같은 유형으로 잘못 분류되는 사례가 반복적으로 나타났다.

- CWE-561: Dead Code
- CWE-563: Unused Variable Assignment

이는 컴파일 과정에서 원본 소스코드의 문법적 특징이 명확하게 보존되지 않을 경우, 모델이 보안약점의 원래 발생 원인을 구분하기 어려워질 수 있음을 보여준다.

따라서 **코드 표현계층에 따른 정보 변화가 CWE 분류 결과에 직접적인 영향을 미칠 수 있음**을 확인할 수 있었다.

### 6.3. 보안약점의 원인과 결과에 대한 해석 차이

일부 오분류는 모델이 보안약점의 직접적인 원인보다 코드에서 관찰되는 동작이나 결과에 주목하면서 발생했다.

대표적인 사례는 다음과 같다.

| 정답 CWE | 모델 예측 CWE |
|---|---|
| CWE-835 (Infinite Loop) | CWE-190 (Integer Overflow) |
| CWE-400 (Uncontrolled Resource Consumption) | CWE-401 (Memory Leak) |
| CWE-400 (Uncontrolled Resource Consumption) | CWE-674 (Uncontrolled Recursion) |

예를 들어 무한 루프가 존재하는 코드에서 모델이 정수 연산과 관련된 특징을 중심으로 판단하면 CWE-190을 예측할 수 있다.

또한 제어되지 않는 자원 소비는 메모리 누수나 재귀 호출과 연관된 실행 양상을 보일 수 있으므로, 모델이 서로 다른 CWE를 관련된 보안약점으로 해석할 가능성이 있다.

이러한 결과는 LLM이 CWE의 정확한 정의만으로 분류하기보다는 **코드에서 나타나는 동작, 보안약점의 발생 원인 및 잠재적인 영향을 종합적으로 고려하여 판단할 수 있음**을 시사한다.

### 6.4. 오분류 분석 종합

오분류 사례는 크게 다음 세 가지로 구분할 수 있었다.

| 구분 | 주요 원인 | 대표 사례 |
|---|---|---|
| CWE 개념 구분 문제 | 유사한 CWE 정의 구분 실패 | CWE-190 → CWE-191 |
| 표현계층 변환 문제 | 고수준 문법 정보의 변화 | CWE-481 → CWE-561/563 |
| 원인·결과 해석 문제 | 보안약점의 원인과 동작 특성 혼동 | CWE-835 → CWE-190 |

이러한 분석을 통해 LLM 기반 보안약점 탐지의 오분류가 단순히 입력 코드의 표현계층 때문에 발생하는 것은 아니라는 점을 확인했다.

즉, **표현계층에 따른 정보 변화와 모델의 CWE 의미 해석 능력이 함께 탐지 결과에 영향을 미칠 수 있다.**

## 7. 연구의 의의와 한계

### 7.1. 연구의 의의

이번 연구는 세 가지 코드 표현계층에 대한 LLM 기반 보안약점 탐지 성능을 여러 모델에서 비교했다는 점에 의미가 있다.

특히 다음과 같은 결과를 확인했다.

- 자체 제작 데이터셋을 통해 기존 공개 벤치마크에 대한 학습 데이터 중복 가능성을 줄이고자 했다.
- 세 가지 LLM을 사용하여 표현계층별 성능 차이가 모델에 따라 다르게 나타날 수 있음을 확인했다.
- CWE 간 의미적 관계를 제한적으로 반영하여 정확한 CWE 일치 여부만을 기준으로 하는 평가를 보완했다.
- 오분류 사례를 분석하여 표현계층 변화뿐 아니라 CWE 개념 및 보안약점 의미 해석이 탐지 결과에 영향을 미칠 수 있음을 확인했다.

특히 이번 연구는 **코드 표현계층에 따른 성능 차이를 확인하는 것에서 나아가, 잘못된 CWE 예측이 발생하는 원인을 분석했다는 점**에서 의미가 있다.

### 7.2. 연구의 한계

본 연구는 10개 CWE 유형과 100개 테스트 케이스를 대상으로 진행되었다.

따라서 실제 소프트웨어 환경에서 발생하는 다양한 보안약점에 결과를 일반화하기에는 한계가 있다.

또한 Cppcheck를 활용한 정적 검증만 수행했으므로, Integer Overflow, TOCTOU, Resource Consumption, NULL Pointer Dereference와 같이 실행 환경 및 입력 조건의 영향을 받는 보안약점에 대해서는 동적 검증이 추가로 필요하다.

Gemini 3.1 Pro의 안전 정책에 따른 응답 거부와 제한된 CWE 관계를 사용한 평가 방식도 결과에 영향을 미쳤을 가능성이 있다.

향후에는 CWE 유형과 데이터셋 규모를 확대하고, 실제 소프트웨어 프로젝트를 대상으로 실험을 진행할 필요가 있다.

아울러 모델별 프롬프트 최적화, 반복 API 질의, 동적 검증, 컴파일러 최적화 수준별 비교를 통해 탐지 성능 차이를 보다 구체적으로 분석할 수 있을 것이다.

## 8. 결론

본 연구에서는 자체 제작한 100개 테스트 케이스를 C 소스코드, LLVM IR, x86-64 Assembly로 구성하고, 세 가지 LLM을 활용하여 보안약점 탐지 성능을 비교했다.

실험 결과, Claude Opus 4.8과 GPT-5.5는 소스코드에서 가장 높은 탐지 성능을 보였으며, Gemini 3.1 Pro는 세 표현계층에서 상대적으로 안정적인 성능을 나타냈다.

또한 CWE 오분류 사례를 분석한 결과, 일부 오류는 코드 표현계층의 변화로 발생했으나 다른 오류는 CWE 정의, 보안약점의 발생 원인 및 실행 결과에 대한 모델의 해석 차이에서 비롯된 것으로 나타났다.

따라서 LLM 기반 보안약점 탐지 성능을 평가할 때는 단순히 코드 표현계층이나 정확한 CWE 일치 여부만을 고려하기보다는, **표현계층에 따른 정보 변화와 CWE 간 의미적 관계를 함께 고려할 필요가 있다.**

## 9. 이전 연구와 달라진 점

이번 연구는 앞서 진행한 **「소스코드 표현계층에 따른 LLM 기반 보안약점 탐지 성능 분석」**을 확장한 연구이다.

두 연구 모두 코드 표현계층이 LLM 기반 보안약점 탐지 성능에 미치는 영향을 분석한다는 공통된 목적을 가진다.

그러나 이번 연구에서는 기존 실험의 범위를 확대하고, 성능 차이가 발생하는 원인에 대한 분석을 추가했다.

### 9.1. 연구 구성 비교

| 구분 | 이전 연구 (ASK 2026) | 이번 연구 |
|---|---|---|
| 연구 목적 | 코드 표현계층별 탐지 성능 비교 | 표현계층 및 모델별 성능 비교와 오분류 원인 분석 |
| 데이터셋 | Juliet C/C++ 데이터셋 | 자체 제작한 100개 테스트 케이스 |
| CWE 구성 | Juliet 기반 실험 대상 | 10개 CWE 유형 |
| LLM | Claude Sonnet 4.6 | Claude Opus 4.8, GPT-5.5, Gemini 3.1 Pro |
| 코드 표현계층 | C/C++, LLVM IR, x86-64 Assembly | C, LLVM IR, x86-64 Assembly |
| 평가 지표 | Accuracy, Precision, Recall, F1-score | 기존 지표 및 제한적 CWE 관계 반영 |
| 추가 분석 | 표현계층별 성능 차이 | CWE 오분류 패턴 및 입력 순서 영향 분석 |

### 9.2. 데이터셋의 변화

이전 연구에서는 Juliet Test Suite를 활용하여 표현계층별 탐지 성능을 비교했다.

Juliet은 보안약점 연구에서 활용되는 공개 데이터셋이지만, LLM이 학습 과정에서 해당 데이터셋을 접했을 가능성을 완전히 배제할 수 없다.

이번 연구에서는 이러한 가능성을 줄이기 위해 10개 CWE 유형을 대상으로 취약 프로그램과 수정 프로그램을 직접 제작했다.

이를 통해 기존 공개 데이터셋에 대한 의존도를 줄이고, 동일한 프로그램을 여러 표현계층에서 비교할 수 있는 실험 환경을 구성했다.

### 9.3. 단일 LLM에서 다중 LLM으로 확장

이전 연구에서는 Claude Sonnet 4.6을 대상으로 실험을 진행했다.

그 결과, C/C++에서 Accuracy, Recall, F1-score가 가장 높았으며 LLVM IR에서는 Precision이 가장 높았다. Assembly는 모든 지표에서 두 표현계층 사이의 성능을 보였다.

그러나 이러한 결과가 다른 LLM에서도 동일하게 나타나는지는 확인하기 어려웠다.

이번 연구에서는 Claude Opus 4.8, GPT-5.5, Gemini 3.1 Pro로 모델을 확장했다.

그 결과 Claude Opus 4.8과 GPT-5.5는 소스코드에서 높은 성능을 보였지만, Gemini 3.1 Pro는 표현계층에 따른 성능 차이가 상대적으로 작았다.

즉, **이전 연구에서 확인한 표현계층별 성능 경향이 모든 LLM에 동일하게 적용되는 것은 아니라는 점**을 확인했다.

### 9.4. CWE 평가 방식의 확장

이전 연구가 표현계층별 탐지 성능을 비교하는 데 중점을 두었다면, 이번 연구에서는 CWE 간 의미적 관계를 평가에 반영했다.

일부 CWE는 상위·하위 관계를 가지거나 발생 원인과 결과가 연결되어 있으므로, 정확한 CWE 번호만을 비교하는 방식에는 한계가 있을 수 있다.

이번 연구에서는 이러한 문제를 고려하여 사전에 정의한 CWE 관계에 대해서만 제한적으로 정답을 인정했다.

이를 통해 CWE 분류 결과를 단순한 번호 일치 여부뿐 아니라, 보안약점 유형 사이의 관계를 고려하여 평가하고자 했다.

### 9.5. 탐지 결과 비교에서 오분류 원인 분석으로 확장

가장 큰 변화는 **탐지 성능 차이가 발생하는 원인을 분석하기 시작했다는 점**이다.

이전 연구에서는 세 표현계층에서 Accuracy, Precision, Recall, F1-score가 어떻게 달라지는지를 비교했다.

이번 연구에서는 오분류 사례를 직접 분석하여 다음과 같은 질문을 살펴보았다.

- 코드 표현계층이 달라져서 보안약점 판단에 필요한 정보가 사라진 것인가?
- 모델이 서로 유사한 CWE 유형을 구분하지 못한 것인가?
- 보안약점의 직접적인 원인과 실행 결과를 혼동한 것인가?

분석 결과, 오분류는 표현계층 변화뿐 아니라 모델의 CWE 의미 해석과도 관련이 있는 것으로 나타났다.

이는 LLM 기반 보안약점 탐지의 성능을 개선하기 위해서는 코드 표현 방식뿐 아니라, 모델이 보안약점의 원인과 특성을 어떻게 이해하는지 살펴볼 필요가 있음을 보여준다.

### 9.6. 연구의 확장 방향

두 연구의 흐름을 정리하면 다음과 같다.

**첫 번째 연구**

코드 표현계층에 따라 LLM의 보안약점 탐지 성능에 차이가 발생하는지 확인했다.

↓

**두 번째 연구**

모델을 확장하여 이러한 성능 차이가 LLM별로 다르게 나타나는지 검증하고, CWE 오분류 사례를 통해 오류가 발생하는 원인을 분석했다.

결과적으로 이전 연구가 **'어떤 표현계층에서 탐지 성능이 높은가?'**에 초점을 맞췄다면, 이번 연구는 **'그러한 성능 차이가 모델마다 어떻게 달라지며, 오분류는 왜 발생하는가?'**라는 질문으로 확장되었다.

이를 통해 LLM 기반 보안약점 탐지에서는 코드의 표현 방식뿐 아니라 모델별 특성과 CWE 간 의미적 관계도 함께 고려해야 한다는 점을 확인할 수 있었다.
