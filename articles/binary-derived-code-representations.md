# [구두발표] 바이너리 유래 코드 표현이 LLM 기반 CWE 탐지 성능에 미치는 영향 분석

**논문 정보**

- **논문명:** 바이너리 유래 코드 표현이 LLM 기반 CWE 탐지 성능에 미치는 영향 분석
- **영문명:** Analysis of the Impact of Binary-Derived Code Representations on LLM-Based CWE Detection Performance
- **저자:** 정서진, 김동엽, 장진수
- **소속:** 충남대학교
- **발표 형태:** 학술대회 구두발표

이번 논문은 직접 구두발표를 진행한 연구로, 기존에 수행했던 코드 표현 계층별 LLM 보안약점 탐지 연구를 바이너리 분석 환경으로 확장한 논문이다.

이전 연구들과 비교했을 때 연구의 목적, 코드 표현 생성 방식, 데이터셋 구성, 성능 평가 기준 등 여러 부분이 달라졌으며, 특히 **실제 바이너리에서 복원할 수 있는 정보를 LLM에 어떻게 제공하는 것이 효과적인가**에 초점을 맞췄다.

---

## 1. 연구 배경 및 목적

실제 소프트웨어 보안 분석에서는 원본 소스코드를 확보하지 못하고 실행 바이너리만 분석해야 하는 상황이 존재한다.

이 경우 역공학(Reverse Engineering)을 통해 프로그램의 구조와 동작을 복원하고, 이를 바탕으로 보안약점을 탐지해야 한다.

그러나 컴파일된 바이너리에서는 변수명, 자료형, 고수준 제어 구조 등 소스코드에 존재하는 일부 의미 정보가 소실되므로 보안약점을 분석하기가 어려워진다.

최근 LLM을 활용한 코드 분석 연구가 활발하게 이루어지고 있지만, 바이너리 환경에서는 LLM에 어떤 형태의 코드를 제공하는 것이 가장 효과적인지에 대한 문제가 남아 있다.

하나의 바이너리에서도 Assembly, Intermediate Representation(IR), Pseudo-code와 같이 서로 다른 추상화 수준의 코드를 추출할 수 있기 때문이다.

이에 본 연구에서는 **동일한 바이너리에서 추출한 세 가지 코드 표현이 LLM의 CWE 탐지 성능에 미치는 영향을 분석**하고자 했다.

궁극적으로는 소스코드가 없는 환경에서 LLM이 바이너리의 취약점을 효과적으로 식별할 수 있도록 지원하는 방법을 탐색하는 것이 연구의 목적이다.

## 2. 연구 방법

### 2.1. 데이터셋 구성

이번 연구에서는 기존 공개 데이터셋의 사전학습 가능성을 줄이기 위해 자체 데이터셋을 구축했다.

CWE 유형은 2025 CWE Top 25와 On the Cusp를 포함한 상위 40개를 후보로 선정한 후, 웹 관련 CWE와 구체적인 코드 패턴으로 표현하기 어려운 Class 수준의 CWE를 제외했다.

이후 Base 및 Variant 수준의 CWE 중 10개를 선정했다.

| CWE | 보안약점 유형 |
|---|---|
| CWE-120 | Buffer Overflow |
| CWE-121 | Stack-based Buffer Overflow |
| CWE-122 | Heap-based Buffer Overflow |
| CWE-125 | Out-of-bounds Read |
| CWE-190 | Integer Overflow |
| CWE-362 | Race Condition |
| CWE-401 | Memory Leak |
| CWE-416 | Use After Free |
| CWE-476 | NULL Pointer Dereference |
| CWE-787 | Out-of-bounds Write |

각 CWE마다 서로 다른 취약 코드 10개를 제작하여 총 100개의 데이터셋을 구성했다.

특히 이번 연구에서는 **코드 복잡도가 탐지 성능에 미치는 영향을 줄이기 위해 순환복잡도(Cyclomatic Complexity, CC)를 11~20으로 제한**하고, Lizard를 이용하여 이를 확인했다.

또한 모든 취약 로직을 하나의 함수에 포함하고 함수명을 `func`으로 통일했으며, 변수명이나 주석 등을 통해 CWE를 직접 추측할 수 없도록 구성했다.

### 2.2. 바이너리 유래 코드 표현 생성

이전 연구에서는 C 소스코드를 LLVM IR과 Assembly로 변환하여 비교했다.

반면 이번 연구에서는 **C 코드를 컴파일하여 생성한 동일한 바이너리를 기준으로, 역공학 도구를 통해 서로 다른 표현을 추출했다.**

생성된 C 코드는 `-O0`, `-arch x86_64` 옵션으로 컴파일했으며, IDA Pro 9.2를 활용하여 다음 세 가지 표현을 추출했다.

| 표현계층 | 특징 |
|---|---|
| Assembly (ASM) | 기계어에 가까운 명령어와 레지스터 연산 중심의 표현 |
| IDA IR | IDA에서 제공하는 중간 표현으로 저수준 동작을 구조화 |
| Pseudo-code | 디컴파일을 통해 복원한 C와 유사한 고수준 코드 |

이때 중요한 점은 원본 C 소스코드를 탐지 모델에 직접 제공하지 않았다는 것이다.

실제 바이너리만 확보한 상황을 가정하여, **동일한 바이너리에서 복원 가능한 코드 표현만을 비교 대상으로 사용했다.**

### 2.3. LLM 및 성능 평가

실험에는 다음 세 모델을 사용했다.

- GPT 5.6 Sol
- Gemini 3.1 Pro
- Claude Sonnet 5

모든 모델에는 동일한 프롬프트를 적용했으며, 외부 검색이나 이전 대화 내용을 활용하지 못하도록 제한했다.

이번 연구에서는 **Accuracy를 주요 성능지표**로 사용했다.

정확도는 모델이 유효한 응답을 반환한 경우를 대상으로 예측 CWE와 정답 CWE가 정확히 일치한 비율로 계산했다.

또한 정확한 CWE 번호를 예측하지 못했더라도 관련된 보안약점을 식별했는지 확인하기 위해 Wu-Palmer(WUP) 유사도를 보조 지표로 사용했다.

WUP은 CWE 계층 구조에서 두 개념의 깊이와 최소 공통 조상(LCS)의 깊이를 바탕으로 유사도를 계산한다.

본 연구에서는 CWE-1000의 계층 관계를 기준으로 정답과 예측 CWE가 조상·후손 관계일 때 WUP을 적용하고, 형제 관계 및 서로 다른 CWE 계열은 0점으로 처리했다.

이는 단순히 CWE 번호를 맞혔는지를 넘어, **모델이 실제 보안약점과 얼마나 관련된 CWE를 예측했는지** 살펴보기 위한 평가 방식이다.

## 3. 실험 결과 및 분석

### 3.1. 코드 표현별 CWE 탐지 성능

**[표 1. 모델별 코드 표현에 따른 CWE 탐지 정확도]**

| Model | Representation | Correct / Valid | Accuracy |
|---|---|---:|---:|
| GPT 5.6 Sol | ASM | 85 / 100 | **0.850** |
| | IDA IR | 79 / 100 | 0.790 |
| | Pseudo-code | 76 / 100 | 0.760 |
| Gemini 3.1 Pro | ASM | 74 / 97 | **0.763** |
| | IDA IR | 59 / 85 | 0.694 |
| | Pseudo-code | 64 / 92 | 0.696 |
| Claude Sonnet 5 | ASM | 41 / 100 | 0.410 |
| | IDA IR | 33 / 100 | 0.330 |
| | Pseudo-code | 49 / 99 | **0.495** |

실험 결과, GPT 5.6 Sol과 Gemini 3.1 Pro는 Assembly에서 가장 높은 정확도를 보였으며, Claude Sonnet 5는 Pseudo-code에서 가장 높은 성능을 기록했다.

특히 GPT 5.6 Sol은 Assembly에서 0.850의 정확도를 기록하며 전체 실험 중 가장 높은 성능을 보였다.

반면 IDA IR은 세 모델 모두에서 가장 높은 정확도를 보이지 못했다.

IDA IR은 평균 입력 길이가 Assembly나 Pseudo-code보다 길었으며, 이러한 입력 길이와 복잡한 표현 구조가 모델의 판단에 부담으로 작용했을 가능성이 있다.

결과적으로 **동일한 바이너리에서 추출한 코드라도 표현 방식에 따라 LLM의 CWE 탐지 성능이 달라졌으며, 모든 모델에 공통적으로 가장 우수한 표현은 존재하지 않았다.**

### 3.2. CWE 오분류 분석

이번 연구에서는 탐지 정확도뿐 아니라 모델이 어떤 CWE를 잘못 예측하는지도 분석했다.

전체 유효 응답 기준 모델별 평균 성능은 다음과 같다.

| Model | Accuracy | WUP |
|---|---:|---:|
| GPT 5.6 Sol | 0.800 | 0.815 |
| Gemini 3.1 Pro | 0.707 | 0.781 |
| Claude Sonnet 5 | 0.411 | 0.471 |

특히 Gemini 3.1 Pro는 CWE-787에서 Accuracy가 0.115에 불과했지만 WUP은 0.850으로 나타났다.

이는 정확한 CWE 번호를 예측하지 못했더라도, 계층적으로 관련된 CWE를 선택한 사례가 많았음을 의미한다.

Claude Sonnet 5의 경우 CWE-121, CWE-122, CWE-125에서 각각 0.133, 0.000, 0.000의 낮은 정확도를 기록했다.

일부 사례에서는 버퍼 관련 취약 동작을 인식했지만, 구체적인 CWE 대신 상위 개념인 CWE-120을 선택하거나 다른 메모리 관련 CWE로 분류했다.

또한 CWE-125(Out-of-bounds Read)를 CWE-129(Improper Validation of Array Index) 또는 CWE-787(Out-of-bounds Write)로 잘못 분류하는 사례가 확인되었다.

이는 모델이 경계 밖 메모리 접근과 관련된 문제를 인식하더라도, **취약점의 발생 원인과 결과, 메모리 접근 방향을 정확하게 구분하지 못할 수 있음**을 보여준다.

반면 CWE-362(Race Condition)는 세 모델에서 각각 1.000, 1.000, 0.967의 높은 정확도를 기록했다.

다만 해당 데이터셋에는 `pthread_create`와 동기화 부재라는 명확한 구조적 특징이 유지되어 있었으므로, 이러한 결과를 일반적인 동시성 취약점 탐지 능력으로 확대 해석하는 데에는 주의가 필요하다.

## 4. 연구의 의의 및 한계

본 연구는 원본 소스코드를 입력으로 사용하는 기존 실험에서 벗어나, **실제 바이너리에서 복원 가능한 코드 표현을 대상으로 LLM의 CWE 탐지 성능을 비교했다는 점**에 의미가 있다.

또한 정확도와 WUP 유사도를 함께 사용하여 취약 동작을 인식하는 능력과 정확한 CWE를 분류하는 능력이 서로 다를 수 있음을 확인했다.

다만 10개 CWE와 100개의 합성 코드를 대상으로 진행했으므로 결과를 모든 소프트웨어 환경에 일반화하기에는 한계가 있다.

특히 모든 취약 로직을 단일 함수로 구성하고 순환복잡도를 제한했기 때문에, 실제 대규모 바이너리에서 나타나는 복잡한 함수 호출 관계나 함수 간 데이터 흐름을 충분히 반영하지는 못했다.

향후에는 여러 코드 표현의 상호 보완 효과를 분석하고, 모델 및 취약점 유형에 따라 적절한 표현을 선택하는 방법으로 연구를 확장할 수 있을 것이다.

## 5. 결론

본 연구에서는 소스코드 없이 실행 바이너리만 확보한 환경을 가정하고, 동일한 바이너리에서 추출한 Assembly, IDA IR, Pseudo-code가 LLM의 CWE 탐지 성능에 미치는 영향을 분석했다.

실험 결과, GPT 5.6 Sol과 Gemini 3.1 Pro는 Assembly에서 가장 높은 정확도를 보였으며, Claude Sonnet 5는 Pseudo-code에서 가장 높은 성능을 보였다.

이를 통해 효과적인 코드 표현은 LLM 모델에 따라 달라질 수 있으며, 코드 표현 자체를 단순한 전처리 결과가 아닌 **LLM 기반 바이너리 분석의 중요한 설계 변수**로 고려해야 한다는 점을 확인했다.

또한 일부 오분류는 모델이 취약 동작을 인식하지 못해서가 아니라, 이를 정확한 CWE 식별자로 연결하는 과정에서 발생했다.

따라서 향후에는 취약 동작 분석과 CWE 분류를 구분하여 지원하거나, 서로 다른 바이너리 코드 표현의 장점을 함께 활용하는 방향으로 연구를 확장하고자 한다.

## 6. 이전 연구들과 달라진 점

이번 논문은 기존의 코드 표현 계층별 LLM 보안약점 탐지 연구에서 발전하여, **연구의 출발점과 분석 대상 자체를 바이너리 중심으로 변경한 연구**이다.

### 6.1. 소스코드 중심 연구에서 바이너리 중심 연구로 전환

이전 연구에서는 동일한 C/C++ 소스코드를 LLVM IR과 Assembly로 변환한 후, 코드 표현 계층에 따른 탐지 성능을 비교했다.

즉, 원본 소스코드가 존재하는 환경을 기준으로 분석했다.

반면 이번 연구에서는 원본 소스코드를 확보할 수 없는 실제 바이너리 분석 환경을 고려했다.

C 코드로 바이너리를 생성한 후, IDA Pro를 활용하여 동일한 바이너리에서 Assembly, IDA IR, Pseudo-code를 추출했다.

기존 연구의 질문이 **'소스코드의 표현 계층에 따라 LLM의 탐지 성능이 어떻게 달라지는가?'**였다면, 이번 연구는 **'소스코드가 없는 상황에서 바이너리로부터 복원한 어떤 표현이 LLM의 CWE 탐지에 유리한가?'**로 변화했다.

### 6.2. 비교하는 코드 표현의 변화

| 구분 | 이전 연구 | 이번 연구 |
|---|---|---|
| 분석 출발점 | C/C++ 소스코드 | 실행 바이너리 |
| 고수준 표현 | 원본 C/C++ | IDA Pseudo-code |
| 중간 표현 | LLVM IR | IDA IR |
| 저수준 표현 | x86-64 Assembly | 바이너리에서 추출한 ASM |
| 코드 생성 방식 | 컴파일러 기반 변환 | IDA 기반 역공학 |
| 주요 분석 환경 | 소스코드 기반 보안 분석 | 바이너리 기반 보안 분석 |

특히 중요한 변화는 **C 소스코드와 Pseudo-code가 동일한 것이 아니며, LLVM IR과 IDA IR 역시 서로 다른 표현이라는 점**이다.

Pseudo-code는 바이너리를 분석해 복원한 코드이므로 원본 소스코드와 동일한 의미 정보를 모두 보존하지 못할 수 있다.

따라서 이번 연구에서는 단순히 기존 입력 코드를 변경한 것이 아니라, 바이너리 분석 환경에서 실제로 활용할 수 있는 표현들을 비교했다는 차이가 있다.

### 6.3. 데이터셋 구성 방식의 변화

이전 연구에서는 10개 CWE에 대해 취약 코드 5개와 수정 코드 5개를 제작하여 총 100개의 테스트 케이스를 구성했다.

이번 연구에서는 10개 CWE마다 서로 다른 취약 코드 10개를 제작하여 총 100개의 데이터셋을 구성했다.

또한 CWE 선정 기준에도 변화가 있었다.

기존 연구에서는 다양한 보안약점 유형을 대상으로 실험했다면, 이번 연구에서는 2025 CWE Top 25와 On the Cusp를 바탕으로 후보를 선정하고, 바이너리 수준에서 분석할 수 있는 Base 및 Variant 수준의 CWE를 중심으로 실험 대상을 구성했다.

특히 이번 연구에서는 순환복잡도를 11~20으로 제한하고 함수명을 통일하는 등 데이터셋의 구조적 차이를 줄이기 위한 조건을 추가했다.

이는 코드 표현에 따른 성능 차이를 확인할 때, 코드 자체의 복잡도가 실험 결과에 과도하게 영향을 주는 것을 줄이기 위한 설계이다.

### 6.4. 평가 방식의 변화: 관련 CWE 인정에서 WUP 유사도로

이전 연구에서는 정답 CWE와 예측 CWE가 정확히 일치하는 경우를 기본적으로 정답으로 판단하고, 사전에 정의한 일부 CWE 관계에 대해서만 관련 CWE 예측을 인정했다.

반면 이번 연구에서는 **정확한 CWE 일치 여부를 평가하는 Accuracy와 계층적 관련성을 평가하는 WUP을 분리하여 사용했다.**

이는 단순히 정답 인정 범위를 확대하는 것과는 다르다.

Accuracy는 모델이 정확한 CWE 식별자를 예측했는지 평가하고, WUP은 정확한 CWE를 맞히지 못했더라도 정답과 계층적으로 관련된 약점을 선택했는지 확인하는 보조 지표이다.

예를 들어 모델이 CWE-121 대신 상위 개념인 CWE-120을 예측했다면, 정확한 CWE 탐지에는 실패했지만 버퍼 오버플로와 관련된 개념을 인식했을 가능성이 있다.

이처럼 **정확한 CWE 분류 능력과 관련 취약점 개념을 인식하는 능력을 구분하여 분석했다는 점**이 이전 연구와의 중요한 차이이다.

### 6.5. 실험 결과와 해석의 변화

이전 연구에서는 Claude Opus 4.8과 GPT-5.5가 원본 소스코드에서 가장 높은 성능을 보였으며, Gemini 3.1 Pro는 세 표현 계층에서 비교적 일정한 성능을 나타냈다.

이번 연구에서는 GPT 5.6 Sol과 Gemini 3.1 Pro가 Assembly에서 가장 높은 정확도를 보였고, Claude Sonnet 5는 Pseudo-code에서 가장 높은 성능을 기록했다.

이러한 결과를 통해 원본 소스코드 기반 실험에서 관찰했던 성능 경향을 바이너리 기반 분석 환경에 그대로 적용할 수 없다는 점을 확인했다.

다만 두 연구는 데이터셋, LLM 모델, 평가 방식 및 코드 생성 환경이 서로 다르므로, 이러한 차이를 표현계층 변경만의 효과로 단정할 수는 없다.

이번 연구에서 중요한 것은 **동일한 바이너리를 대상으로 비교하더라도 모델마다 적합한 코드 표현이 달라진다는 사실**이다.

### 6.6. 연구 목표의 변화

이전 연구의 주요 목표는 코드 표현 계층에 따른 탐지 성능을 비교하고, CWE 오분류가 발생하는 원인을 분석하는 것이었다.

이번 연구에서는 이를 바탕으로 실제 바이너리 분석에서 LLM에 어떤 정보를 제공해야 하는지에 더 집중했다.

또한 단순히 취약점을 탐지했는지를 확인하는 것을 넘어, 모델이 취약 동작은 인식했지만 이를 정확한 CWE로 분류하지 못하는 현상에 주목했다.

이를 통해 향후 연구에서는 취약 동작을 이해하는 과정과 CWE를 최종 분류하는 과정을 구분하거나, 서로 다른 코드 표현 및 구조 정보를 결합하여 LLM의 분석을 보조하는 방향으로 확장할 수 있을 것이다.

## 7. 구두발표 기록

이번 논문은 학술대회에서 직접 구두발표를 진행했다.

앞서 작성한 논문들이 코드 표현 계층에 따른 LLM의 보안약점 탐지 성능을 비교하는 데 중점을 두었다면, 이번 발표에서는 이러한 연구를 왜 바이너리 분석 환경으로 확장하게 되었는지, 기존 연구들과 어떤 차이가 있는지를 설명하는 것이 중요했다.

특히 원본 소스코드를 입력하는 방식과 실제 바이너리에서 복원한 Pseudo-code를 입력하는 방식은 동일하지 않다는 점, 그리고 LLVM IR과 IDA IR의 차이를 구분하여 전달하고자 했다.

또한 실험에서 GPT와 Gemini는 Assembly에서, Claude는 Pseudo-code에서 가장 높은 성능을 보인 이유와, 정확한 CWE 탐지에 실패했더라도 취약 동작 자체는 인식할 수 있다는 점을 중심으로 연구 결과를 설명했다.

이번 연구를 통해 **LLM 기반 보안약점 탐지에서 중요한 것은 단순히 모델에 코드를 입력하는 것이 아니라, 분석 환경에 적합한 정보를 어떤 형태로 제공할 것인지 고민하는 과정**이라는 점을 다시 확인할 수 있었다.

앞으로는 이번 연구에서 얻은 결과를 바탕으로 바이너리에서 추출할 수 있는 다양한 코드 표현과 구조 정보를 활용하여, LLM의 보안약점 분석을 보조하는 방향으로 연구를 발전시키고자 한다.
